# 任务中枢与文档治理：详细设计与施工方案

日期：2026-09-19。

状态：用户已于 2026-09-19 确认，授权在 `feat/task-hub-doc-governance` 分支施工。本文为设计基线，实际实施及验证结果见对应任务记录；下文的“本轮仅出方案”等表述保留原提案时点含义，不覆盖最新用户授权。

设计依据：本次讨论确认的需求；当前 `legacy` 分支的实现及旧方案仅作参考。不以兼容旧命令、旧配置或旧文档为目标，也不在本轮迁移或清理任何旧内容。

## 1. 产品目标与边界

产品定位为面向个人开发者及其 Agent 协作的任务中枢，提供三项核心能力：

1. **文档治理**：找到当前有效的项目说明，维护明确的知识落点，减少过时、冲突与重复内容。
2. **任务接续**：在更换会话或模型后，以少量阅读恢复目标、执行边界、当前进度和下一步。
3. **分层模型协作**：廉价模型负责定向探索和范围明确的施工，高级模型负责关键核实、设计与偏差决策，最终由用户选择验收方式。

成功标准是交接后少补查、少误解、少返工，并保持文档可信。文件数、命令数和正文长度是成本指标，不能单独代替质量标准。

### 1.1 本版包含

- 两份核心任务文件及按需拆分的详细材料。
- 探索、设计、施工、验收四种角色的工作与交接约定。
- 当前文档导航、文档有效性标记、变更联动和知识沉淀。
- 可独立使用的 Skill，以及共享相同约定的完整工具包。
- 少量用于定位、提取上下文、检查明确错误的程序能力。

### 1.2 本版不包含

- 自动选择或调用模型、API 密钥管理、费用路由、后台任务调度。
- 多 Agent 抢占任务、锁、事件总线或自动合并系统。
- 强制 CI、复杂审批流、逐候选处置账、全局编号和目录注册系统。
- 向量数据库、全仓自动摘要、周期性扫描与自动判定知识价值。
- 旧版配置迁移、旧命令别名或历史文档批量转换。

首版允许用户手动切换模型，由文件完成交接。自动调度须在真实流程已证明有效后另行决定。

## 2. 两种交付形态

| 能力 | 单 Skill 版 | 完全体 |
|---|---|---|
| 任务流程、模型角色、文档维护规则 | 完整提供 | 使用同一份 Skill |
| 任务文件与必要模板 | Skill 自带 | 使用同一套模板 |
| 任务定位与接续 | 普通目录查询和文件读取 | 工具提供简短列表与上下文提取 |
| 定向阅读 | 根据固定章节与明确引用读取 | 按角色、任务编号提取确定章节 |
| 文档检查 | Agent 在相关范围检查 | 程序检查明确的结构和引用问题 |
| 运行条件 | 具备文件读写能力的 Agent | 额外需要工具运行环境 |

**单 Skill 版交付单位是一个可复制的 Skill 目录，不强求只有一个文件。** 目录可以包含入口、分角色说明和两个模板；全部相对引用随目录分发，不能依赖 CLI 初始化产物、包内隐藏路径或外部服务。

两版读取、写入相同任务文件。安装工具后不转换格式，移除工具后仍能继续工作。完全体不增加一套独立状态库。

## 3. 消费项目的信息结构

建议默认结构如下，目录按需要创建：

```text
docs/
  README.md                    文档导航与当前有效落点
  <主题文档或主题目录>          产品、设计、约定、指南等
  tasks/
    2026-09-19-标题搜索/
      state.md                 当前状态、进度、执行边界、索引
      details.md               探索依据、当前方案、施工单元、结果
      references/              仅在确有长材料时创建
```

不预建八类目录。一次会话即可完成、无需接续的小任务，可以直接执行和更新项目文档，不强制建任务。

任务名称由日期和可读名称组成；T1、T2 等编号仅在该任务内有效。文件存在本身不意味着获准施工，也不意味着设计已经确认。

项目协作指令仍由项目自身维护。本产品不自动修改项目权限规则、提交策略或用户的模型选择约束。

## 4. 两份核心任务文件

### 4.1 state.md：唯一进度入口

保存以下内容：

- 本任务目标摘要及完整目标的位置。
- 当前阶段、执行边界与已获授权的方案版本；尚无授权时明确写明。
- 当前子任务和各子任务状态。
- 会影响下一步的阻塞或待决定问题。
- 下一步动作及必读材料指针。
- 必要的结果索引，正文证据留在详情。

建议使用 `探索 / 设计 / 施工 / 待验收 / 完成` 五个阶段。暂停与阻塞作为说明字段，保留原阶段，避免另造复杂状态组合。

子任务进度使用 `未开始 / 进行中 / 待处理 / 已自检`。整项任务进入“完成”，依据用户选择的验收方式和实际验收结果；“已自检”不能自动等同于“已验收”。取消任务明确标记“已取消”和原因，不冒充完成。

这是人工与 Agent 共用的状态约定，不实现自动状态机。程序可提取和检查结构，不从正文推断授权或自动推进阶段。

示例中的路径仅用于说明，非本仓实际实现：

```markdown
# 标题搜索

## 当前
目标：增加标题子串筛选，保留原排序和键盘操作。
阶段：施工
执行边界：用户已授权执行方案 r1；发布不在范围内。
当前：T2。T1 已自检，最终验收尚未开始。
阻塞：无。

## 进度
| 任务 | 状态 | 说明与结果 |
|---|---|---|
| T1 纯过滤函数 | 已自检 | details.md 的 T1、结果 T1 |
| T2 接入输入事件 | 未开始 | details.md 的 T2 |
| T3 使用说明 | 未开始 | details.md 的 T3 |

## 下一步与阅读
执行 T2；先读 details.md 的“共同约束”“当前设计”“T2”。
按 T2 指针核实 src/search.js 的输入处理与相关测试。
结果证据见 details.md 的“执行结果”；完整验收见“验收要求”。
```

状态文件以一屏至数屏能理解为目标，常规任务可先以约 500–1000 中文字整理。该数值是写作提示，不是截断阈值或门禁。内容增长时，把详细解释移回明确落点，保留当前限制、未解问题和索引。

### 4.2 details.md：执行依据与按需详情

建议采用少量稳定的二级标题；执行单元使用稳定局部编号：

```markdown
# 标题搜索详情

## 目标与验收
完整需求、明确不做的范围、最终验收方式与条件。

## 探索结果
相关入口、调用关系、已有测试、证据定位、疑点与未查看范围。

## 共同约束
各施工单元都必须遵守的约束，包括需求边界和用户决定。

## 当前设计
方案版本 r1；当前有效的实现选择、接口、数据流及关键理由。
待决定事项明确单列；未决事项影响的单元不能作为可执行单元交付。

## T1 纯过滤函数
一个完整施工单元。

## T2 接入输入事件
另一个完整施工单元。

## T3 使用说明
文档维护施工单元。

## 执行结果
按 T1/T2/T3 记录实际结果、验证范围、遗留与证据。

## 发现与经验
尚需接续或值得沉淀的发现；已进入正式文档的仅留必要引用。
```

详情不维护第二份进度表。执行结果是事实与证据，当前状态由 state.md 汇总。正常阅读不要求把探索结果、执行结果和经验全文一起加载。

方案包含复杂专题时，保留概要和明确指针，将专题拆到独立文件。实际交接必须把该任务的必读专题列出，不能靠执行者猜测其重要性。

### 4.3 拆分与保留原则

- 两个核心文件始终存在；额外文件只服务实际阅读或交付需求。
- 共同约束保持精炼。只约束某个单元的内容放在该单元，防止所有执行者重复支付成本。
- 大段日志、外部资料和实验原文按需外置，并说明支持什么结论；默认不进入接续材料。
- 当前设计采用替换更新。必要的被否决方案仅保留结论与原因，不保留逐轮对话。
- 未解问题、验收条件与关键用户决定不能为缩短文件而被省略。

## 5. 四阶段工作流与交接

### 5.1 定向探索：廉价模型

输入为用户原始目标、探索范围、必要项目指令和已有任务状态。探索者可以整理目标，但必须区分用户要求与自身推测。

探索交付至少包括：

1. 相关入口、核心实现、直接调用方、关联数据结构和测试位置。
2. 当前行为与关键调用关系的短说明。
3. 重要判断的文件、符号或章节依据；行号只作辅助，因为会变化。
4. 与任务相关的当前文档，以及发现的代码／文档不一致。
5. 疑点、尚未核实的前提和未查看范围。

探索以足以支持设计讨论为停止条件；委派时设置文件或调用预算，预算耗尽后回传已知与未知，不继续扩大全仓阅读。具体预算按任务大小确定，不在产品里固定为统一次数。

不得把搜索未命中写成“代码库不存在该能力”，也不得把建议写成已确认需求。关键关系不清时应明确报告缺口。

### 5.2 核实、讨论与设计：高级模型

高级模型根据探索定位直接核实关键源码与测试，不重复全仓扫描。核实深度按变更风险决定，不能为了节省 token 只阅读二手摘要。

设计阶段负责明确目标与验收，解决重要的接口、数据流、边界行为和取舍，列出文档影响，并拆分施工单元。多轮讨论持续更新当前设计、用户决定与待决定事项。

方案达到可执行程度的判断依据：下一位执行者能够知道改哪里、遵守什么、如何验证，以及何时回交；不要求预先解决所有局部命名和代码排版。

用户授权执行的范围与当前有效方案版本记录在 state.md。已有明确授权继续有效，无需为了格式索要固定口令。本次会话的“确认执行前仅讨论”仍适用；本文交付不构成实施授权。

### 5.3 分项施工与最低自检：廉价模型

每次领取一个完整、可验证的执行单元。先读状态、共同约束、当前设计及该单元，再核实指定代码前提。工具提取出的材料不能代替对实际文件的必要核实。

执行者可以决定范围内的普通实现细节。出现下列情况，停止受影响单元并回传：

- 关键接口或行为与方案前提不一致。
- 必须扩大修改范围、改变用户已确认行为或增加方案未包含的重要依赖。
- 验收条件互相矛盾，或必要设计决定尚未确定。
- 验证失败源于设计问题，或连续尝试没有新增有效信息。

无须对每个可自行解决的小错误回交。回传应包含期望、实际观察、定位证据、已尝试的相关处理和需要的决定，避免只写“做不了”。

完成单元后，执行最低充分验证并记录证据，再更新状态。环境不支持的验证写成“未验证”及原因；不得修改验收标准来制造通过。

### 5.4 最终验收：用户选择

用户可以自行验收、指定高级模型验收，或提前授权按明确检查结果判定完成。产品不强制高级模型复审所有任务。

验收材料包括目标与验收条件、当前有效设计、变更范围、执行结果和未验证项。查看相关 diff、运行结果或实际行为；没有具体疑点时不再做全仓探索。

未通过项回到具体施工单元或设计决定。验收通过后标记完成，保留简短结果和必要文档链接；无须额外收口文件或搬目录。

## 6. 可执行施工单元的写法

一个单元围绕可观察结果拆分，不按“读文件、改一行、运行命令”机械拆碎。依赖必须明确；互相依赖到无法独立验证的修改可以组成一个单元。

每个单元按需包含以下内容，复杂任务必须把关键项说清：

| 项目 | 内容 |
|---|---|
| 目标与验收 | 完成后的行为和本单元可验证的结果 |
| 依赖与前提 | 上游结果、需要先确认的代码事实 |
| 必读材料 | 文件、符号、章节，注明必读或参考 |
| 修改范围 | 允许修改的文件或职责边界，以及本次不处理的内容 |
| 实现路径 | 高级模型已决定的数据流、接口、边界行为和实施顺序 |
| 最低验证 | 与风险直接相关的检查、预期输出或行为 |
| 回交条件 | 需要重新决策的偏差 |
| 回传要求 | 实际改动、验证结果、未验证项和遗留 |

### 6.1 示例：T2 接入输入事件

这是结构示例，文件与函数名称是假设，不是已经核实的仓库接口。

- **目标**：输入变化后按标题筛选，保留原排序；中文输入法组合输入期间不提前筛选。
- **依赖**：T1 的过滤函数已自检；开始前核实其接口及相关测试结果。
- **必读**：共同约束、当前设计、`src/search.js` 的输入绑定、指定的输入事件测试；无需读取早期方案比较全文。
- **范围**：搜索输入的状态与事件处理及相关测试；不修改排序算法，不引入全文搜索依赖。
- **实现路径**：输入进入组合状态时暂停筛选；组合结束后以当前值触发筛选；普通输入沿用既有更新路径；空输入恢复全部项目。实际事件绑定方式须与现有实现匹配，避免重复触发相同更新。
- **验证**：普通输入、清空输入、组合输入过程、组合结束后的结果，以及筛选后原排序保持；验证方式由设计阶段根据现有测试能力指定。
- **回交条件**：输入处理由另一组件控制，接入必须改变其对外接口；或者现有状态模型无法表达方案要求。
- **回传**：修改位置、实际验证及未验证的浏览器行为、是否存在剩余边界问题。

方案不能保证任意低能力模型都能正确实现。执行模型至少需要具备局部代码理解、编辑和验证能力；真实演练用于判断任务粒度和说明是否足够。

## 7. 方案修订、接续与并行边界

### 7.1 版本与授权

details.md 的“当前设计”标明方案版本，例如 r1。state.md 记录用户授权适用的版本与范围。版本是任务内简单标记，不建立版本数据库。

改变需求、接口、验收或关键实现路径时更新方案版本，并注明受影响的单元。普通澄清、错字或定位修正无需升级版本。

新版本不因写入文件自动获得授权。原授权能否覆盖修订，依据用户已给范围判断；未授权的重大取舍需要用户决定。未受影响且仍在原授权范围内的任务不必一律重启。

执行者发现当前设计与记录的执行边界不一致时，应明确核实适用范围。工具只能揭示版本或结构差异，不能替用户批准方案。

修订者同时在 state.md 标出受影响单元。已经施工的受影响单元改为“待处理”，说明需调整还是需重新验证；旧结果保留适用版本，不能继续作为新版本通过的证据。未受影响单元沿用既有证据，不默认要求全部重做。

### 7.2 记录责任

- 探索者写探索依据并把下一步交给设计者；不能把自己的建议登记为用户决定。
- 设计者维护当前设计、共同约束、执行单元和修订影响；仅根据实际用户指令更新执行边界。
- 顺序施工时，执行者记录结果并更新当前单元状态；并行施工时只回传，由主会话整合两份文件。
- 验收者或接收用户验收结果的主会话记录结论，再更新整体阶段。未选择验收方式时保持待验收。
- 回交问题记录在 details.md 对应单元的“待决定”处，state.md 只留阻塞摘要和指针；由当前主会话交给高级模型或用户，不假定存在后台自动路由。

先写详细依据和结果，再更新状态摘要。若中断造成两者不一致，下次根据实际文件与证据修正，不能单靠摘要宣称完成。

### 7.3 中断恢复

先读 state.md，再定位本角色需要的详情。与当前动作有关的易变事实从实际文件核实，旧测试结果不能证明新修改后的代码仍通过。

存在未记录修改时，先核对相关 diff 或实际文件，再修正状态。Git 可辅助核实，但不是单 Skill 版的运行前提；无 Git 时按指定文件和可用证据核实，不承诺重建未保存的思考。

主会话收到新需求，应将它归入已有任务或明确的新范围，不能覆盖尚未完成工作的状态。

### 7.4 多模型与并行

首版默认顺序交接。确有互不冲突的子任务时，可以由主会话委派并行实现；主会话统一整合 state.md 和 details.md，执行者回传结果，避免多人同时编辑中心记录。

不新增抢占、锁或任务调度服务。不同工作区的成果仍通过正常差异审查整合。

## 8. 文档治理设计

### 8.1 文档入口与分类

docs/README.md 维护按主题组织的主要入口，回答“哪个问题去哪里看”。它不枚举所有文件，不镜像任务进度，也不与配置维护三方一致性。

少量文档可以直接列在项目 README 中；完全体默认使用 docs/README.md，有既有入口时通过显式路径选择读取。首版不需要通用目录配置系统。

正文区分三种适用性：

- **草案**：尚未确认或实施的提案，明确哪些部分仍待决定。
- **现行**：本主题当前采用的说明，并注明未覆盖的范围。
- **历史**：已被替代或只用于回溯的记录，文首说明原因和当前落点。

建议用简短文首说明和普通 Markdown 链接，不强制所有文档填写 id/type/line/created 等字段。格式标记只能表达作者声明，不能证明内容正确。

### 8.2 当前结论的维护

同一事实选择一个主要维护位置，其他文档引用。设计时发现冲突，应明确冲突点与依据，不能自动以最新日期或当前代码覆盖用户已确认的约束。

修改现行说明通常直接更新原文。确需保留独立旧方案时标记历史并指向替代文档；文档入口更新为当前落点。历史材料默认不进入接续上下文。

机器可以检测引用存在性，不能可靠判断两个不同标题的文件是否在表达相互冲突的规范；后一项由定向阅读与设计核实处理。

### 8.3 文档维护贯穿任务

| 阶段 | 文档治理动作 |
|---|---|
| 探索 | 定位相关现行文档，指出不一致及未确认内容 |
| 设计 | 明确需要新增或更新的文档，纳入相关施工单元及验收 |
| 施工 | 随行为变化更新实际受影响的说明，避免复制第二份规范 |
| 验收 | 检查相关文档与交付行为是否一致，确认必要长期结论已落位 |

不是每次代码修改都必须新增文档。有相关影响就维护；判断无影响时简短说明即可，不填“无提升”处置表。

### 8.4 发现、经验与任务完成

执行中尚未确认的发现保留在详情，带依据和不确定性。已确认且有长期复用价值的结论，直接整理到对应主题文档；任务详情保留接续需要的摘要或引用。

不默认创建无限增长的总经验库。经验有共同主题时自然归入指南、设计或故障处理说明；没有长期价值的过程信息不强制提升。

任务完成后保留原目录和两份文件，状态改为完成，正常任务列表默认省略。无需归档迁移或登记账；历史删除与集中整理只在用户需要时进行，不能让产品自动删除用户工作材料。

## 9. Skill 的组织与触发

建议交付目录：

```text
skills/worklog/
  SKILL.md
  references/
    exploration.md
    design.md
    implementation.md
    acceptance.md
    governance.md
  templates/
    state.md
    details.md
```

入口只说明适用场景、当前阶段识别、角色路由、共同原则及记录位置。分角色说明按需读取，模板仅在创建或修复结构时读取。不得把所有参考文件列成每次必读。

治理说明在涉及文档判断或首次建立相关约定时加载；共同的必要要求在入口简述，避免施工模型因未读治理全文而漏掉方案中明确列出的文档任务。

用户明确要求规划、接续、按方案执行或管理项目文档时使用；有跨会话需要的任务可以建议或建立记录，但必须遵循用户对写文件和执行的限制。快速问答不因命中关键词就创建任务。

入口不能假定宿主支持自动模型切换、后台运行或自动加载所有 Skill 文件。没有自动加载能力时，用户可直接指定入口文件。

## 10. 完全体工具边界

首版只设计三个用户可见入口，具体参数在实现前以最小可用方式定稿，不增加旧命令别名：

| 入口 | 职责 | 写入行为 |
|---|---|---|
| init | 安装或导出 Skill，提供最小项目接入说明 | 仅显式请求时写入；不覆盖本地定制，不注入 CI |
| context | 列任务或按指定任务、角色、单元提取材料 | 只读，默认输出到调用方，不生成另一份持久状态 |
| check | 检查指定任务或文档范围的明确结构及引用问题 | 只读，默认不自动修复 |

建任务、更新状态、记录结果、结束任务仍由 Agent 编辑普通文件。用户不必掌握命令，通过自然语言表达目的即可。

### 10.1 context 的提取规则

- 无指定任务时只给任务名称、阶段与状态入口；多个候选不擅自选取。
- 普通接续只给 state.md 及明确的阅读路径。
- 所有指定任务的角色材料都包含 state.md；以下列出追加的必需内容。
- 探索角色读取“目标与验收”中的已知要求和探索范围，追加已有共同约束与相关疑点；尚未设计的内容可明确标为待定。
- 设计角色读取“目标与验收”“探索结果”“共同约束”“当前设计”和相关待决定事项。首次设计时“当前设计”可明确标为尚未形成，不能伪造方案。
- 施工角色必须指定单元；读取状态、共同约束、当前设计和该单元。单元须包含与自己相关的验收要求，不能只写一个泛泛的“见总验收”。
- 验收角色读取完整验收条件、当前设计、执行结果和遗留项，附相关变更定位；不默认注入所有探索历史。

以上是材料组合规则，不包含自动语义压缩。章节过长时由规划者整理或拆分，程序不能悄悄截掉关键内容。

施工单元内的“目标与验收、依赖与前提、必读材料、修改范围、实现路径、最低验证、回交条件、回传要求”使用稳定小标题，按第 6 节约定定位。没有依赖或额外材料时写明“无”，不留占位符。请求施工材料时，这些字段和共同约束、有效设计为必需项；目标、关键路径或验收仍待定的单元应返回缺项说明。验收角色必需“目标与验收”“当前设计”“执行结果”；尚未执行的检查在结果中明确写为未验证。解析器能识别缺节及约定的待定标记，但不能证明自然语言内容足够完整，语义可执行性仍由设计者负责。

必读引用显式标记，与参考资料区分。首版只提取清楚声明的任务内章节或受支持的本地文件片段，不自动递归展开所有链接。源码引用输出定位指针，执行者再针对性读取当前源码。

必需章节、指定单元或必读引用缺失时，明确返回缺项，不提供假装完整的执行材料。检测到同名定位不唯一时要求修正定位。格式完整也不能被标记为“已经获准执行”。

任务文档、源码、日志各自标明来源；引用资料是证据，不能借此覆盖用户或项目指令。输出不混入未选任务和无关历史。

### 10.2 check 的检查范围

保留以下可明确判定的检查：

- 任务两份核心文件及被请求阶段必需的章节是否存在。
- 状态引用的施工单元和本地必读材料是否可定位，章节是否重复歧义。
- 管理范围内的本地 Markdown 文件链接是否可达；受支持的章节引用是否存在。
- 声明的文档替代目标是否存在。

语义重复、结论过时、任务真正完成、方案质量由 Agent 或用户判断。首版不做外部网址联网检查，不扫描所有代码字符串来猜文档引用。

检查按显式指定的任务或文档范围运行；未指定范围时使用清楚说明的默认文档范围。文本输出只列问题、位置和原因，通过时给短结果。退出状态区分成功、发现问题和输入／运行错误，便于用户自行接入自动化。

默认不设置合并门禁，不要求每个编辑动作都执行检查。相关批次完成后做一次必要检查即可。

## 11. 代码组织与旧实现取舍

建议保留现有语言方向，以少量 Node 模块实现完全体；具体最低版本以实施时环境与发布策略确定，不在讨论阶段升级依赖。

建议按职责分为：命令入口、初始化、任务定位与章节提取、本地文档引用检查、少量文件读写辅助。共享逻辑只在实际重复时提取，不建通用工作流引擎、插件框架或配置 DSL。

| 旧能力 | 新设计处置 |
|---|---|
| 多版本 schema、upgrade、baseline | 不进入新模型，无兼容迁移需求 |
| trio/lite/team 多套任务表示 | 统一为两份核心文件和按需详情 |
| 候选全局编号、closeout 处置校验 | 以文档影响与实际验收替代 |
| 工作线实体、生成式状态副本、目录登记一致性 | 以文档入口与直接任务发现替代 |
| 大量 start/note/checkpoint 等命令 | 使用普通编辑，工具只保留额外价值明确的入口 |
| Markdown 识别、路径处理、可靠写入 | 检查新需求后按需参考或复用，不自动保留整个旧层级 |

运行代码与测试分开，避免把维护者自检暴露为日常产品命令。模板和 Skill 分角色说明只有一套源文件；完全体分发同一内容，不手工维护复制版本。

对新产品确实执行的写入保留必要保护：初始化不覆盖用户定制，错误时明确说明实际写入结果。删除复杂旧机制不等于删除基本正确性。

## 12. 成本控制与实际评价

总成本包括探索、设计、施工、记录维护、验收与返工。高级模型多核实几处关键实现，可能降低总成本；廉价模型重试很多次也可能更贵。

采用以下策略：

- 探索带范围、预算和停止条件，输出结论与依据而非完整阅读日志。
- 高级模型按定位核实，只针对信息缺口追加探索。
- 施工一次领取一个可验证单元，公共材料与当前单元按需读取。
- 状态有实质变化、暂停或交接时更新；不按工具调用次数记录。
- 验收从条件、差异和证据出发，存在具体风险才扩大审查。
- 同一事实维护一个主要正文，其他文件使用短摘要和指针。

首轮观察指标：各角色读取的文本量、额外读写调用、补充探索次数、因材料缺失产生的回交、返工次数，以及最终结果正确性。取得真实调用用量时才统计 token 和费用；字符量不能冒充账单。

验收不要求固定节省百分比。若切片工具的开销超过直接读取收益，应缩减工具，而非增加更多调度层。

## 13. 后续施工分批方案

所有批次须在用户确认实施后开展。每批形成完整可评估结果；不以运行旧门禁为新产品验收目标。

| 批次 | 交付 | 最低充分验证 |
|---|---|---|
| A：约定与单 Skill | 入口、角色说明、两份模板、一个完整示例 | 检查内部引用；用独立目录进行无 CLI 的探索—设计—施工交接演练 |
| B：上下文提取 | context、任务发现、确定章节及必读材料提取 | 对实际样例验证不同角色读集、缺项报错、无关内容排除；不运行自动摘要 |
| C：文档检查与接入 | check、init、简单使用说明 | 有效／失效本地链接、歧义章节、缺失单元；初始化不覆盖已有文件 |
| D：产品收敛 | 最终 README、打包范围、旧实现退役 | 审查变更；在临时消费项目验证单 Skill 与完全体共享格式；做一次实际包交付冒烟 |

批次 A 先验证交接质量。若独立模型无法按材料完成任务，先修正方案写法和任务粒度，不立即追加自动调度。

退役旧实现前依据本方案核对范围，并保护当时已有的用户改动。本计划不授权改写 Git 历史、远端发布、全量依赖升级或任意清理工作区。

## 14. 验收场景

以下为后续实施必须演练的结果，本轮尚未执行：

| 场景 | 通过条件 | 失败信号 |
|---|---|---|
| 陌生施工模型接续 | 只收到用户指令、Skill 和项目文件，能定位当前单元、约束与验收并完成范围内工作 | 必须读取整段历史对话；漏读关键约束；误做未授权工作 |
| 探索报告有缺口 | 报告明确未知，高级模型按定位补查相关部分后设计 | 将推测当事实；高级模型必须从头全仓扫描 |
| 只讨论尚未授权 | 状态、角色说明和实际行为一致，只更新方案或明确允许的材料 | 看到任务清单或完整提取结果就开始改产品代码 |
| 方案发生实质修订 | 受影响单元能识别有效版本与执行边界，旧方案不会被误用 | 施工继续按被替代接口执行；新设计自动被视为批准 |
| 施工前提不成立 | 执行者回传具体差异和证据，由高级模型或用户决定 | 擅自扩大修改范围；修改验收标准；无依据重复重试 |
| 自检完成、用户尚未验收 | 状态保持待验收，证据与未验证项清楚，用户能选择验收方式 | 自动标记全任务完成；用旧验证证明新代码通过 |
| 文档变更与历史治理 | 更新相关现行文档，历史材料标明替代落点，长期知识不只留在任务详情 | 设计草案被当现行规范；产生相互冲突的正文；断链未暴露 |
| 两版一致与按需阅读 | 同一任务可在两版之间接续，无格式转换；当前单元材料完整，无关历史不默认加载 | Skill 引用工具安装后才有的文件；两版行为漂移；缺项被静默省略 |

机械验证采用与新能力相关的局部测试，不迁移旧测试数量目标；一次代表性真实交接演练补足格式检查无法证明的行为质量。没有新变化或失败证据，不重复运行整套验证。

## 15. 当前结论与实施前待定项

本方案建议采用：两份核心任务文件、按角色阅读、范围明确的施工单元、用户选择最终验收、完整文档治理，以及共享同一约定的单 Skill／完全体。

下列事项在确认实施时定稿，不影响当前讨论的产品核心：

1. 是否采用本文建议的目录名和三个工具入口；参数写法由最小实现决定。
2. 最终验收默认保持“待用户选择”，还是允许项目预先约定自动完成的明确条件。
3. 首次交接演练使用的真实任务与模型组合；遵循用户当时允许的模型，不在产品中硬编码提供商。

本轮没有实现、安装、发布或进行产品运行验证。本文交付后等待用户讨论或明确确认执行。
