## 二、审查发现与最小修改

### R1 · P1：全局进度的读取路径没有覆盖未挂主题的任务

**依据：** 原方案 §2（L38）、§7（L133–147）、§12.2（L265）、§16（L354）。

**问题：** 方案允许任务不建立主题文档，但全局进度的阅读与验收规则只明确要求聚合相关主题。这样可能遗漏合法存在、正在执行但未挂主题的独立任务。虽然已有 `context --list` 兜底，它尚未被明确接入全局汇总流程。

**最小修改：** 询问项目整体进度或全部待办时，在读取全局说明与相关主题之外，用 `context --list` 枚举未完成任务，再按回答需要读取相关 state；无 CLI 时浏览任务目录完成等价定位。普通单任务施工不增加这一步，也不要求 todo 登记全部任务。

同时明确：全局说明必须有一个已选定的落点；可选的是“是否新建 `项目推进.md`”，不是“是否保留全局视图”。这一点延续 §7 的要求，不另设进度表。

**通过条件：** 一个任务没有主题入口、也不在 todo 中，但仍在进行；询问全局进度时能够发现它，不把已选工作完成误报为全局完成。

### R2 · P1：事项部分解决、分阶段承接的回收规则不完整

**依据：** 原方案 §8（L151–161）、§11（L246）、§16（L351）。

**问题：** §8 已要求“删除已解决的开放条目”，但随后又概括为“完成时删除对应开放条目”，没有明确一个主题事项由多个任务分阶段承接时的处理。任务的验收范围可能小于原事项范围，完成一个任务不代表整个事项已经解决。

例如，一个事项同时涉及桌面端与移动端，本次任务只完成桌面端；不能因此删除整个开放事项及其仍有效的工作选择入口。

**最小修改：** 允许同一事项锚点关联多个承接任务。任务完成后，只把已解决范围写入“当前现状”；仍需处理的范围留在开放事项中，写明剩余问题、启动条件或后续任务指针。任务内部未通过验收的内容，仍不得通过移回主题来制造任务完成。

回收 todo 时按条目代表的范围判断：已完成任务的条目撤下；仍被选中的剩余事项保留或改指其主题锚点。只有事项全部解决或明确放弃，才删除整个开放条目。

**通过条件：** 同一事项由任务 A、任务 B 分阶段承接；任务 A 完成后可更新成果，但任务 B 对应的剩余事项仍可发现，不重复保存已完成范围的正文。

### R3 · P1：单元设计下沉后，验收的补读责任没有接上

**依据：** 原方案 §10（L215–235）、§16（L349）。

**问题：** 方案要求公共“当前设计”只保留概要，单元专属设计及其必读材料放入 T 单元；但验收的“精确读集”不包含 T 单元，也不包含“共同约束”。普通链接又不自动展开，因此默认验收输出可能缺少实际适用的设计和约束。现有验收场景检查了施工的 T1/T2 隔离，未覆盖这一验收路径。

这并不意味着验收者不能手动读取，而是当前协议没有明确要求补读，容易仅根据结果摘要判断通过。

**最小修改：** 区分“CLI 默认输出”与“完成验收所需阅读”。在“执行结果”保留本次验收单元及依据指针；验收者沿指针补读相关单元设计、适用的共同约束和约束片段。明确这是验收职责的一部分，而不是可省略的背景阅读。

无需新增 CLI 参数，不把全部单元设计塞回公共章节，也不改变工具只展开一层必读的规则。

**通过条件：** T1 有公共概要未复述的专属约束；验收者能够定位该约束并识别不符合要求的结果，同时无需加载无关的 T2 材料。

### R4 · P2：无角色输出三节还是全文，表述不统一（本轮已按源码修正）

**依据：** 原方案 §10（L219–225）、§12.3（L274）、§12.6（L295）。

**问题：** §10 将无角色读集写为 state 的三个章节，§12 又写为只输出 state 文件并保留现行行为。若 state 含额外章节，两种表述可能导向不同实现；本次未读取模板，不能断言当前输出已经存在差异。

**最小修改（原建议，经源码核实不成立）：** 原建议以 §12 的保留现行行为为准，统一写成：

> `context <任务>` 不带 `--role` 时输出 state.md 全文，不展开必读；指定角色时再按角色表选取章节。

「全文」这一表述与源码不符：`src/lib/taskdoc.mjs:9` 定义 `STATE_SECTIONS = ['当前', '进度', '下一步与阅读']`；`src/context.mjs:211` 按该常量逐个构造 sources，`:229` 只在无 role 时跳过必读展开，`:244–250` 再逐个输出这些 sources。因此现行行为本就是三节切片，state 里的额外章节不输出。**修正后的最小修改：** 保持现行三节切片，统一写成「`context <任务>` 不带 `--role` 时输出 state.md 的「当前」「进度」「下一步与阅读」三节，不展开必读，额外章节不自动输出；指定角色时再按角色表选取章节」，同步修改 §10 的无角色行、§12.3 与 §12.6 的表述，不改动其他角色的默认输出。

**通过条件（修正后）：** 使用含一个额外小节的 state，确认无角色输出只有「当前」「进度」「下一步与阅读」三节，额外小节不出现，且其中的必读链接不展开。

## 四、保留的边界与实施要求

保留正文单一落点、任务 state 作为本任务进度权威、索引链接不自动展开、显式必读只展开一层，以及日常不逐轮维护全套文档的规则。不增加全局编号、强制元数据、自动摘要同步或 token 门禁。（依据：原方案 §2、§9–12。）

人工维护可能过期、工具不能移除已进入会话的材料、`check` 不能验证语义，这些限制原方案已经明确，不应再次当作遗漏，也不能在实施说明中扩大效果承诺。（依据：原方案 §19。）

上述四个通过条件（R4 按本轮修正后的版本）可尽量复用 §15 的代表性任务与已有测试；只补真实缺失的场景，不扩建测试体系。原方案关于链接检查覆盖范围、Skill 导出及参数解析现状的陈述，留到相关实施批次做定向核实，不能以本次设计审查代替代码验证。
