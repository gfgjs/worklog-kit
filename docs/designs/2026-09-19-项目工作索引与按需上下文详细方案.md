# 项目工作索引与按需上下文：详细方案

日期：2026-09-19。

状态：r4 已按用户后续指令授权施工，实施与简单验证记录见 [施工任务](../tasks/2026-09-19-项目工作索引/state.md)，完整验收由其它会话执行。下文“本轮仅修订”“尚未实施”“未授权”等保留提案时点含义，不覆盖后续授权。第 18 节推荐已采纳，全局现状落点确定为 [项目推进](../topics/项目推进.md)。

设计依据：本轮讨论中用户明确提出的问题与约束，以及主会话据此给出的结构建议。仓库现有工具、Skill 与文档只作现状材料；本文不含已完成的实施，也不构成实施授权。

## 0. 标记约定

本文区分三类内容：用户本轮**已确认**的要求与约束（方案按此设计）；主会话给出的具体形态（目录名、分组规则、命令细节），属**推荐**，待用户审阅后定案；以及当前仓库的实际**现状**，用于说明改动量与兼容性。第 18 节的未决选择保持未决。

用户已确认：缺项目全局当前进度与待办；旧版 todo 长期膨胀；README 与 todo 必须极简或仅作索引，细节按需读取；长程任务初次加载的大材料会长期占用上下文。目标形态是极简入口、按需阅读、补齐全局缺口。

本轮仅修订本文档与同目录审查报告；产品代码、Skill、模板、CLI、发布与提交不在范围。[文档导航](../README.md)的草案入口是上一轮登记的事实，本轮不再改动该文件。

## 1. 要解决的问题

| 问题 | 表现 | 本方案的处理层 |
|---|---|---|
| 缺全局当前进度与待办 | 只有各任务自己的 state.md，项目整体「现在做到哪、还剩什么」没有落点 | todo 的工作选择索引，加已指定并优先复用的全局现状落点 |
| todo 长期膨胀 | 全量未完成事项堆在一个文件里，背景、阶段、进度都写在条目上 | todo 只写短名称加链接，正文进主题文档与任务 |
| README 与 todo 变成内容文件 | 导航文件越写越细，每次打开都要读大段细节 | 两个文件只做索引，目标一屏左右 |
| 长程任务的大材料长期占用上下文 | 某轮为施工读入的大段材料在后续轮次继续占据窗口 | 主题按章节读、任务材料按角色切片、详细解释留在 details |

## 2. 三层索引与执行材料

| 层 | 文件 | 回答的问题 | 维护内容 |
|---|---|---|---|
| 入口 | `docs/README.md` | 去哪里看 | 主要落点，以及草案、现行、历史文档的关系 |
| 入口 | `docs/todo.md` | 先做什么 | 当前重点、下一批、其他事项 |
| 主题 | `docs/topics/<主题>.md` | 当前能力、限制与后续事项 | 当前现状、开放事项、相关任务、依据与约定 |
| 任务 | `docs/tasks/<日期任务>/state.md` | 这个任务现在到哪一步 | 唯一进度表、阶段与执行边界 |
| 任务 | `docs/tasks/<日期任务>/details.md` | 方案、证据与详情 | 设计、施工单元、执行结果、发现与经验 |

三层依次是入口、主题、任务，职责各自单一：README 只回答「去哪里看」，todo 只回答「先做什么」，主题文档只回答这块当前是什么能力、有什么限制、后面还要做什么，任务 state 是本任务执行进度的唯一权威，details 装方案与证据。一个事项只在一处写正文，其余位置用短名称加指针。

三层是按需落点，不是每个改动的固定流程：直接指定的任务仍从该任务 state 进入；独立的一次性小改沿用现有轻量处理；只有需要长期保留的现状或候选、或需要跨任务接续时，才维护相关专题。复用已有专题优先；全局说明优先指定已有的产品规划文档，确无落点时再新建。没有真实主题需求时不必为了凑层级先建主题文档。日常只维护 state 与 details，仅在现状、工作选择或入口实际变化时同步相关专题、todo 与 README，不逐轮维护全套；小事不强制建立任务目录。

明确不引入：第二张进度表、工作线注册表、全局事项编号、固定元数据字段、复杂状态机、自动摘要同步。

## 3. 目录与文件布局

建议的基础布局如下。目录按实际需要创建，不要求把所有旧材料迁移过来：

```text
docs/
  README.md                    文档导航：去哪里看
  todo.md                      工作选择索引：先做什么
  topics/
    <主题>.md                  按主题的现状、开放事项、相关任务、依据与约定
    <主题>/                    主题正文过长时才按真实领域拆分
  tasks/
    <YYYY-MM-DD-可读名称>/
      state.md                 本任务执行进度（唯一）
      details.md               方案、单元、证据与详情
      references/              确有长材料时创建
```

三条落位规则：

1. 已有合理的现行专题文档直接复用，一个主题只保留一处正文。已有的产品方案、使用说明、约定文档就是主题正文，不必为了新结构另建一份。
2. 不把每个待办建成独立文件。待办是主题文档里的一个事项小节，只有成为任务时才有独立目录。
3. 默认不建 `backlog.md`、`completed.md`、`project-state.md`。未立项的候选留在主题文档的开放事项里，已完成事项不累加总库。

## 4. README：文档导航

职责是回答「哪个问题去哪里看」。建议只列几个主要目的地，例如：本项目的产品与设计基线、使用说明、待办索引、按主题的现状文档、任务记录的根目录。

写法约定：

- 不枚举目录内所有文件，不镜像任何进度或统计。
- 每个落点一行，写明「想找什么」和去处。
- 草案、现行、历史文档的关系在文首或文末说清，历史材料的替代落点随更新同步。
- 维护本文件不要求逐轮编辑，只在落点变化时更新。

## 5. todo：工作选择索引

建议固定三个二级标题，顺序本身表达优先级：

| 分组 | 装什么 | 条目里的链接指向 |
|---|---|---|
| 当前重点 | 正在做或下一步就要做的少数事项 | 已立项的任务 state、全局现状文档的目标节，或已选中但尚未立项的主题事项锚点 |
| 下一批 | 明确准备做、尚未开始的事项 | 任务 state 或主题文档的具体事项章节 |
| 其他事项 | 知道存在、暂不排期的事项 | 只给主题级入口，不深链到具体事项 |

条目写法：短名称加普通相对链接，可带锚点。不写背景、阶段、进度、已完成数或时间线。示例：

```markdown
## 当前重点
- 项目的全局现状与目标：[topics/项目推进.md#当前总目标](topics/项目推进.md#当前总目标)
- 尚未立项但已选中的事项：[topics/渲染性能.md#长列表滚动卡顿](topics/渲染性能.md#长列表滚动卡顿)
- 上下文入口收敛：[tasks/2026-09-19-项目工作索引/state.md](tasks/2026-09-19-项目工作索引/state.md)

## 下一批
- 主题文档模板与示例：[topic-template](topics/主题文档约定.md#模板与示例)

## 其他事项
- 发布与打包：[topics/发布.md](topics/发布.md)
```

维护规则：

- 同一事项不同时出现在「当前重点」和「下一批」。它的位置表达当前选择。
- 「当前重点」可以直接指向主题事项的锚点。事项尚未立项时没有任务目录，仍能从 todo 发现并定位。
- 其他事项里的主题入口允许覆盖当前任务所在主题。这是导航，不是重复正文。
- todo 是人工选择，不保证登记全部未完成任务。需要全量清单时用显式工具或直接看任务目录，见第 12 节的 `context --list`。
- 某个分组没有内容就写「无」，不留空标题。
- 条目回收按第 8 节。

## 6. 主题文档：现状与开放事项

建议四个二级标题，但不作为强制 schema；按主题的真实情况取舍。

| 章节 | 内容 |
|---|---|
| 当前现状 | 当前能力与限制、验证边界。用原位替换更新，不写变更历史 |
| 开放事项 | 每个事项一个可读且稳定的局部标题，正文写问题或期待结果、来源、启动条件或待决定信息 |
| 相关任务 | 承接该主题事项的任务指针 |
| 依据与约定 | 该主题的长期约定、依据与已确认决定 |

事项写法：

- 标题要可读且稳定，能长期作锚点被 todo 和任务引用；改标题时同步修所有活链接。
- 只写问题或期待结果、来源、启动条件或待决定信息，不预写实现方案与进度。
- 按需要写，不强制填满固定字段，不造空表。
- 已确认值得后续处理即可登记，不要求已经排期；未核实或尚无结论的发现留在任务 details。

跨主题的问题选一处作为正文落点，其余位置用引用。主题正文过长、难以定位时，再按真实领域拆分或把长设计移出，并修复链接。

## 7. 跨主题目标与全局现状

拆成主题后，项目的总目标和整体进度必须有一个已选定的落点，优先复用已有的产品规划文档及对应章节；只有确实没有合适落点时，才按需新建 `docs/topics/项目推进.md` 作为该落点。待定的只是「指定哪一份文档、是否新建」，不是「是否保留全局视图」。

该落点维护四类内容：

- 当前总目标，以及本阶段要达成什么。
- 阶段性成果与关键缺口。
- 跨主题依赖。
- 主题文档链接。

定位说明：

- 它是一份主题正文，不是每轮必读文件，也不是第二份任务进度库；单个任务的进度仍只在任务 state.md。
- todo 的「当前重点」可以链接它的目标节，用来表达阶段性选择。
- 在用户询问全局进度、全部待办或跨主题依赖时按需读取：读取该全局说明与相关主题，并用 `context --list` 枚举未完成任务、按回答需要读取相关 state；无 CLI 时浏览任务目录完成等价定位。
- 普通单任务施工不增加这一步，也不要求 todo 登记全部任务。
- 不凭 todo 单独宣称全局已完成：todo 是人工选择索引，既不保证全量登记，也不表达完成度。

## 8. 事项进入任务与回收

一个主题事项成为任务后，正文不复制：主题侧改成短问题名称加承接任务指针并保留原锚点，需求、验收与进度写进任务的 details 与 state，主题不再复述任务细节。

同一事项锚点可以关联多个承接任务，也允许部分承接：已承接范围的正文只存在任务里，未承接的剩余范围继续留在主题的开放事项中，写明剩余问题、启动条件或后续任务指针。任务完成只更新它已解决的成果，剩余事项、启动条件与任务指针仍可被发现。

以下是任务关闭后回收规则的唯一主说明：

| 事件 | 主题侧动作 | todo 侧动作 |
|---|---|---|
| 任务完成，且该事项全部解决 | 已解决成果更新到该主题的「当前现状」；删除整个开放条目 | 撤下该事项的工作选择条目；无关条目与仍有导航价值的主题入口保留 |
| 任务完成，但事项仍有未解决范围 | 只把已解决成果写入「当前现状」；保留开放条目，改写剩余范围、启动条件或后续任务指针 | 按条目代表的范围回收：已完成任务的条目撤下，仍被选中的剩余事项保留或改指其主题锚点 |
| 任务取消或暂停 | 只要还可能继续处理，就保留开放事项并写清再启动条件 | 按能否继续决定条目是否保留与所在分组，保留时指向可继续的主题事项或任务 |
| 明确放弃 | 从开放事项移除，必要时在「依据与约定」留一句结论与原因 | 撤下该事项的工作选择条目 |

取消或暂停不等于解决。任务验收范围内未完成的内容，不得通过移回主题来制造任务完成。只有整个事项解决或明确放弃，才删除整个开放条目：删除时把仍有证据价值的来源引用改指「当前现状」节或任务结果，来源引用与 todo 条目不同，该事项的 todo 条目是撤下而不是改指结果页。暂停或取消时是否保留开放条目与 todo 条目按上表决定。仍有导航价值的主题入口保留；必要的历史过程只留在任务目录，不累加成完成总库。

### 8.1 短示例：一个事项从候选到全部解决

同一事项的三个阶段，只保留当前有效状态（路径与链接为模拟）。本例前提是事项全部解决；若只部分承接，完成后按上表保留开放条目并改写剩余范围，而不是删除。

未立项，候选留在主题开放事项：

```markdown
## 开放事项
### 长列表滚动卡顿
问题：列表超过 200 行时滚动掉帧。启动条件：待定，需先确认可接受的帧率口径。
```

立项后，同一锚点改为指向任务，主题不复述：

```markdown
### 长列表滚动卡顿
已立项：[长列表滚动优化](../tasks/2026-09-19-长列表滚动优化/state.md)
```

完成后原位更新现状、删除开放条目、撤下对应的 todo 条目：

```markdown
## 当前现状
首屏改为增量渲染，达到任务约定的验收条件。
验证边界：只验证了桌面 Chrome 与示例数据规模。
来源：[执行结果](../tasks/2026-09-19-长列表滚动优化/details.md#执行结果)

## 开放事项
无
```

具体操作：候选与立项期间保持同名锚点，便于 todo 与任务长期反查；事项全部解决时 todo 撤下该条目而不是改指结果页，只部分承接时保留或改指剩余事项锚点；有证据价值的引用改指现状或结果，主题导航按需保留；「相关任务」只留仍在进行或需要反查的指针，不登记该主题的全部历史任务。

## 9. 更新时机与恢复

日常：施工只更新本任务 state 与 details；主题、todo 与 README 仅在现状、工作选择或入口实际变化时同步，不逐轮维护全套。发现与立项、优先级调整等时机见第 5、6 节，任务关闭的回收见第 8 节。任务关闭的状态侧动作沿用现有阶段模型：完成与已取消照旧，「暂停」用 state 现有字段写明并保留开放事项，不新增阶段。

主会话整合：并行子代理只回传单元结果，共享索引与主题文档由主会话统一更新，单个单元的细节不触动全局文件。

写入顺序：先写事实与证据（任务 details、主题现状），再更新 state 摘要，最后按影响更新 todo 与 README；不为「写回」全仓扫描。

恢复：先用 state 定位任务与下一步，再按当前动作核实相关 diff 与证据，据此判断是否真的完成；不泛查全仓 diff，也不凭总览文件或修改时间武断判定完成。

## 10. 阅读协议

按请求的类型决定入口：

- 未指定具体工作：读 `docs/todo.md`，选中对应主题章节或任务 state，再按角色读取材料。
- 询问全局进度或全部待办：按第 7 节读取全局说明与相关主题，并用 `context --list` 枚举未完成任务、按回答需要读取相关 state；无 CLI 时浏览任务目录完成等价定位。单任务施工不增加这一步。
- 明确指定任务：直接读该任务 state，按需要展开章节。
- 角色材料：沿用现行四角色切片规则，不因新增主题层而改变。
- 施工角色：仍然只加载 state 加「共同约束」「当前设计」与指定单元，不自动注入 README、todo 或全部主题。

各角色的 CLI 默认输出与现行一致：

| 角色 | 读取内容 |
|---|---|
| 无角色（只给状态） | state.md 的「当前」「进度」「下一步与阅读」三节；state 里的额外章节不自动输出 |
| 探索 | 上述 state 三节，加 details 的「目标与验收」，存在时加「探索结果」「共同约束」 |
| 设计 | state 三节，加「目标与验收」「探索结果」「共同约束」「当前设计」 |
| 施工 | state 三节，加「共同约束」「当前设计」与指定单元 |
| 验收 | state 三节，加「目标与验收」「当前设计」「执行结果」 |

上表是 CLI 的默认输出，不是完成一次验收所需的完整读集：执行结果里记录本次验收单元及其依据指针，验收者沿指针补读相关 T 单元设计、适用的共同约束与约束片段，不加载无关单元。这是验收职责的一部分。补读不新增 CLI 参数，也不改变工具行为。

这些都是文件片段，不含语义压缩；新增主题层不改变这些切片，任务材料的采集方式保持现有 `context` 行为。无角色同样只输出上述三节，不因为 state 里有额外章节而多输出。

必读标记与普通引用的区分：

- 索引文件里的普通链接绝不自动展开，包括看起来像「必读」的内容。
- 涉及主题约束时，在任务被选中的章节里显式标注：`必读：[名称](相对路径.md#锚点)`，一行一个。
- 必读按角色输出时生效：工具从所有被选中章节收集并展开一层必读，不递归展开引用里的引用；无角色时只输出 state 的上述三节，不展开必读。各角色的章节读集以上表为准。
- 因此公共章节（state、共同约束、当前设计）只写共用概要与共享必读，单元专属设计及其分片必读放进对应 T 单元的小节。需要从公共章节指向单元专属设计时用普通链接导航，由执行者按需打开，不自动展开。
- implement 下，公共章节里的必读对每个 `--unit` 都同样展开，不按单元筛选；工具不新增按单元过滤公共分片的能力，按单元生效靠材料落位。

必读只按显式声明展开：工具不识别语义依赖，片段内部还有依赖时必须在任务里显式写清；普通引用与必读严格区分，格式齐全不代表已获授权执行。

## 11. 上下文增长控制

| 位置 | 目标写法 | 硬边界 |
|---|---|---|
| README、todo | 一屏左右读完，只做索引 | 写作提示，不做行数、字节或 token 门禁，不截断文件 |
| 主题文档 | 只读相关章节 | 不要求整篇加载 |
| state.md | 简短，写当前进度与指针 | 详细解释进 details 或按需材料 |
| details.md | 按单元与角色切片 | 不相关章节不必一起加载 |

已加载的材料不会因为文件被修改而自动消失，当前会话继续用已加载的有效材料；只在任务或设计实质变化、交接或恢复时重读相关部分，不每轮强制重跑提取。换会话或换模型由 state 接续，不重走全局材料。任务大到一个 state 难以接续时，按可独立验收的结果拆成多个任务，不机械拆分也不虚假关闭。主题大到难定位时按真实领域拆分或移出长设计并修复链接；todo 主题入口过多时优先删除无关入口、复用现有分组导航，确有规模再引入按需的主题分组索引，不预建更多索引层。

## 12. 工具行为：context / check / init

### 12.1 `context`（无参数）

目标行为：

| 情况 | 行为 | 退出码 |
|---|---|---|
| `docs/todo.md` 存在且可读 | 输出来源标识加 todo 原文，末尾一句提示 `context --list` | 0 |
| 不存在 | 回退现有 listTasks 输出，未采用本结构的项目仍可用 | 0 |
| 存在但为空或全为空白 | 明确报出 todo 为空 | 1 |
| 存在但不是文件（如目录），或读取失败 | 明确报出路径或读取问题 | 2 |

要求：不展开 todo 里的链接、不列所有任务、不附加 README、不做语义摘要、不做长度截断。todo 里没有任务但有候选事项时照常输出。不静默回退成「没有工作」。

### 12.2 `context --list`

新增显式开关，调用现有 listTasks：全量未完成任务按原约定显示，包括缺少 state 的提示；已完成与已取消任务仍需显式指定任务名查看。它不依赖 todo，也不展开任何主题文档。询问全局进度或全部待办时用它枚举未完成任务，再按回答需要读取相关 state；它只枚举任务，不提供全局现状正文，全局说明与相关主题仍需按第 7 节单独读取。无 CLI 时浏览任务目录完成等价定位。

### 12.3 参数组合与错误

| 组合 | 处理 |
|---|---|
| `--list` 与任务位置参数、`--role`、`--unit` 同时出现 | 互斥，退出码 2 |
| 无任务却携带 `--role` 或 `--unit` | 退出码 2，明确报错 |
| `--help` / `--version` | 保留现行优先级，写在任何位置都只打印帮助或版本 |
| `context <任务>` 且无 `--role` | 只输出 state.md 的「当前」「进度」「下一步与阅读」三节，不展开任何必读（保留现有行为） |
| `context <任务> --role ...` | 从 state 与所选 details 章节收集一层必读，行为不变 |

任务目标仍是任务路径。主题文档不能当作 `context` 的目标；读取主题用 Agent 的文件能力或任务里的显式必读行，不新建通用 reader 命令。

### 12.4 `check`

现有的普通 Markdown 链接与锚点检查已经覆盖 todo 与主题文档，因此不新增检查项：不强制项目必须建立主题目录或指定主题文件、不枚举标题、不检查事项是否全量登记、不判断事实新鲜度、不判断优先级、不判断授权。已经写进文档的本地链接目标与锚点仍须存在，沿用现有 `check` 判定。`check` 只做结构判定，不能宣称已验语义。项目没有 todo 是合法状态。

### 12.5 `init`

继续整目录导出 Skill。新增的 todo 与 topic 模板随 Skill 目录自然导出，`init` 不需要为此改代码。`init` 不创建消费项目的 todo、不修改 AGENTS。无 todo 时的回退只给建议，不写入。

### 12.6 状态差异与兼容性

以下现状由上一轮源码核对与命令实测确认，目标是本方案建议的形态，尚未实施；r4 本轮只补入无角色三节切片的源码依据：

- `context` 无参数：现状直接输出 listTasks 列表（0）；目标优先输出 todo 原文并提示 `--list`，无 todo 时回退列表。
- `context --list`：现状判为不支持参数（2，`context 不支持的参数：--list`）；目标为合法开关，输出全量未完成任务。
- 无任务时携带 `--role`：现状静默返回任务列表、角色被忽略（0）；目标报错（2）。

`context <任务>` 无 `--role` 时只输出 state 的三节（「当前」「进度」「下一步与阅读」）且不展开必读、`--role implement` 无 `--unit` 报错，这两项保持不变。state 里的额外章节不在默认输出内。

实现时需要在入口解析里真正识别 `--list`，并把无参数情形交给 `runContext` 处理（`bin` 的布尔旗标目前未被解析）。

## 19. 风险与限制

- 索引依赖人工更新，不更新就会过期；`--list` 与任务目录只提供全量兜底，不解决登记遗漏。todo 是人工选择集合，不能据它推断全部未完成任务或全局完成度。
- `check` 只判定结构与引用，不判断语义、事实新鲜度或事项优先级；检查通过不代表约定被遵守。
- 工具不能移除对话内容，也不能接管宿主的上下文管理，本方案只减少需要新读入的材料，不声称降低实际计费比例。
- 主题约束变化只能由主会话更新已知受影响的任务，执行前核实所需主题段；无法自动证明全仓任务都已同步。
- 结构本身有维护成本：没有真实主题需求就不预建主题文件，用不到的可选部分可以省略；移除已有内容前先核实落点与活链接，不保留无人维护的空骨架。
