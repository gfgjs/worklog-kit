# worklog：任务文档

用项目里的普通 Markdown 保存接续信息，每个任务一份 `docs/tasks/<稳定名>.md`。任务列表即时派生，不维护静态索引、配置或归档。

## 何时用

- 任务明确：在项目根跑 `worklog-kit read <任务路径>`，先读当前摘要与详情目录；需要细节时按返回的行号读取相关部分，确需全文才加 `--full`。
- 任务不明确：先列 `docs/tasks/`，或在项目根跑 `worklog-kit list [关键词]` 筛选，按需细读，别全量读所有任务。
- 一次完成且无接续需要的小任务（单文件改动、快速问答）不建档。
- 建档时机：第一次出现值得跨会话保留的信息才创建文件；没有就不建。

## 文件格式

- 位置：`docs/tasks/<稳定名>.md`，目录平铺。名字用稳定可读的短名（中文可用），不带日期、编号或工作线，路径本身就是身份。
- frontmatter 只写三个非空单行字符串字段：

```yaml
---
title: 稳定、可读的任务名
status: active
summary: 一句话当前状态
---
```

- `status` 取 `planned`（已认可的计划）、`active`（进行中）、`done`（完成）、`cancelled`（明确停止）。开工改为 active，重开也使用原路径；阻塞写在当前摘要里。
- 正文必须有一个非空的 `## 当前`，包含目标与完成标准、当前落点、继续工作依赖的关键决定及理由、未解问题或阻塞、下一步。
- 之后可以有 `## 详情` 或任意其他二级标题放按需细节。代码围栏里的标题不算标题。

## 与正式文档的关系

任务的正式成果（API 契约、部署步骤、设计结论）放在它们自己的项目文档里；任务文档只保留接续需要的当前状态，并指向那些文件的准确路径或章节，不复制全文。

## 写什么

- 只写从代码和实际状态中难以低成本恢复的信息：已确认的约束与决策（带原因）、未解问题、下一步。
- `## 当前` 原位替换当前事实，同步更新一句话 summary，不追加“第 N 轮”“今日进度”，过期内容直接删。
- 完成的工作保留结论、验证方式或链接，以及仍重要的理由；不写命令输出、过程日志、思考流水，也不存仓库快照（文件列表、依赖版本、提交号）——这些随时可读，只有作为接续必需的验证证据或定位线索时才保留。
- 长期有效的内容直接更新对应正式文档（README、规范等），不在任务文档复制第二份，也不建全局记忆副本。
- 只在出现改变接续的事实、决定或阻塞时更新，不在每次工具调用后写记录。
- 不写密钥、token、生产配置。

## 接续与协作

- 恢复工作先读 `## 当前`，再按需展开详情；以文件为准，不用记忆里的印象替代。
- 影响下一步的易变事实（某测试当前是否通过、某文件是否已存在）从实际文件或本次运行结果核实；旧记录里的“通过”不代表现在仍然通过。
- 一任务一文件。一个任务由主会话把多个子代理的结果整合进同一份文档；子代理只回传必要结果。
- 改动前先读已有内容，只更新与本任务相关的事实。

## 结束

- 完成必要验证后（文档等无需测试的任务以实际完成为准），把有长期价值的内容写进正确落点，把 `status` 改为 `done`，保留该文档作为结果与验证记录，不移动、不归档、不删除。
- 仍有认可但未完的工作：维持 `active`，写清当前落点与下一步。
- 用户明确停止任务时改为 `cancelled`，在当前摘要保留停止原因。
- 尚未验证或部分完成不要标 `done`；写过记录不算完成证明，完成依据是工作本身与必要的验证。

## 没有 CLI 时

直接用文件读写完成以上动作。在项目根跑 `worklog-kit list` / `worklog-kit read <路径>` 只是方便汇总与查看，不是必需；不要为使用本 Skill 安装旧版 npm 包或生成索引。
