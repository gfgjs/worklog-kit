# 文档治理

任务记录之外的文档如何保持可信。涉及文档落点、有效性判断、断链或知识沉淀时读本文件。

## 入口与落点

- 文档入口回答「哪个问题去哪里看」。文档少时直接列在项目 README，多时用项目文档目录的 README。入口只列主要落点，不枚举所有文件，也不镜像任务进度。
- 同一事实只在一处维护正文，其他位置写短摘要加指针。发现冲突时点明冲突点与依据，不自动以最新日期或当前代码覆盖用户已确认的约束。

## 三种适用性

- **草案**：尚未确认或实施的提案，写明哪些部分待决定。
- **现行**：本主题当前采用的说明，注明未覆盖的范围。
- **历史**：已被替代或只用于回溯，文首说明原因与当前落点。

用短小文首说明加普通链接即可，不强制填元数据字段；标记只表达作者声明，不能证明内容正确。

## 维护贯穿任务

| 阶段 | 动作 |
|---|---|
| 探索 | 定位相关现行文档，指出不一致与未确认内容 |
| 设计 | 明确要新增或更新的文档，纳入相关单元与验收 |
| 施工 | 随行为变化更新受影响的说明，避免复制第二份规范 |
| 验收 | 核对文档与交付行为一致，确认长期结论已落位 |

不是每次代码改动都要写文档：有相关影响就维护，判断无影响就简短说明，不填「无提升」处置表。

## 发现与经验

- 未确认的发现留在任务详情，带依据与不确定性。
- 已确认且有长期复用价值的结论，整理进对应主题文档（指南、设计、故障处理说明都行）；任务详情保留摘要或引用。
- 不建无边界增长的经验总库；过程信息没有长期价值就不提升。

## 完成与保留

任务完成后保留原目录与两份文件，阶段改「完成」；正常任务列表默认省略已完成任务。产品不自动删除用户的工作材料，历史清理只在用户需要时做。
